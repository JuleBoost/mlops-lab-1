Lab 1 - Answers to the questions

1. Observe the files created, what do you think they contain.

Running uv init gave pyproject.toml, README.md, .python-version, and a src folder with a starter package (an __init__.py with a main function). pyproject.toml holds the project name, Python version requirement and the list of dependencies. .python-version pins which Python version the project expects. Once dependencies get added with uv add, it also creates uv.lock (the exact locked versions of every dependency, so installs are reproducible) and a .venv folder (the actual virtual environment with everything installed).

2. What are the created files. What do you think they are used for? And which ones should be pushed to git?

dvc init creates a .dvc folder and a .dvcignore file. Inside .dvc there is a config file (where the remote name and URL live, safe to commit), a config.local file (where credentials like username and password end up, meant to stay local and never be committed), a tmp folder, and a .gitignore that DVC writes itself so config.local, tmp and its cache never get committed by accident. .dvcignore works the same way .gitignore does, but for DVC instead of git.

Out of all of that, only .dvc/config and .dvcignore should go to git. config.local should never be pushed since it holds credentials.

3. Where are the credentials stored? and what are the options other than --global? Should the credentials be pushed to github?

Credentials are stored with --local, which writes to .dvc/config.local inside the project folder. The other option is --global, which stores them outside the repo entirely, in a config file under the user's own system folder (on Windows that's under AppData), meaning they'd apply to every DVC project on that machine rather than just this one. We went with --local, which is also what DagsHub recommends in its own setup instructions.

Credentials should never be pushed to GitHub. That's exactly why config.local is git-ignored by default.

4. Take a look at the .gitignore file. Explain what happened.

Before running dvc add data, the data folder wasn't tracked by git but it also wasn't ignored, so git would have picked up every single image file if we tried to add everything. Once we ran dvc add data, DVC added a line for /data straight into .gitignore automatically. Now git ignores the actual folder completely, and the only thing that gets committed is data.dvc, the small pointer file that represents it.

5. Do you see a .dvc file? What does it contain?

Yes, data.dvc. It's a small text file with the md5 hash of the whole data folder, the total size in bytes, and the number of files it contains. That hash is what DVC uses to know exactly which version of the data belongs to which commit, and it's also what it uses to fetch the right files back from the DagsHub remote when you run dvc pull.

6. You can check your main branch on the github web UI. Is the code there? Is the data there? Do you have any file that points to the data location. And what about dagshub web UI do you see the data?

On GitHub, the code is there (pyproject.toml, the src folder, etc.) along with data.dvc, but none of the actual images, since those were never tracked by git in the first place. data.dvc is the file that points to where the data lives. DagsHub also acts as a git remote, so the same code and data.dvc pointer show up there too. The actual images only show up on DagsHub once dvc push finishes copying them into DagsHub's storage, addressed by content hash rather than stored as regular git files.

7. In a completely new temporary folder clone your github repo. Do you see the data folder? What dvc command is needed to get the data folder?

Right after cloning, the data folder is either missing entirely or shows up empty, since git never stored the actual image files, only the data.dvc pointer. Running dvc pull is what actually downloads the images from the DagsHub remote, using the hash stored in data.dvc to fetch the matching snapshot.

8. Do you still see the new folders you created? food11_processed and food11_processed_mini?

No. Checking out an older commit from before those folders were added, then running dvc checkout, makes food11_processed and food11_processed_mini disappear from the working directory, since that older commit's data.dvc pointer doesn't include them. Checking out main again and running dvc checkout brings them right back.
