Lab 4 - Answers

1. What happens to everything written to /mlflow-data if you never mount a volume there and just
docker run this image standalone? Try it: run the container, register nothing, stop it, remove
it, start a new one from the same image - what do you see in the UI?
It is lost with the container, since it only lived in its writable layer. Tested: created
experiment "q1-probe", it was in /mlflow-data/mlflow.db; after rm + new container from the same
image the UI showed only "Default".

2. Why a named volume here instead of a bind mount to a folder in your repo (the way you might
for local dev)? Would a bind mount work just as well?
A bind mount would persist too, but it pins the stack to one host path and inherits host
permissions/path quirks, and the server state would sit inside the repo. The named volume is
managed by Docker, portable, and created/removed with the stack. Bind mounts suit code you edit
live, not opaque server state.

3. In Lab 3 you had to use host.docker.internal or --network host to reach mlflow from inside the
container. In this lab, MLFLOW_TRACKING_URI will simply be http://mlflow:5000. Why does that
hostname resolve now when it didn't before?
Compose puts the services on one user-defined network with an embedded DNS that resolves each
service name to its container. In Lab 3 the container was alone on the default bridge, where no
such name exists, so it had to go back out through the host.

4. Why does the frontend read INFERENCE_URL from an environment variable instead of hardcoding
http://inference:8000? Think about what happens if you ever docker run this frontend image on
its own, outside Compose.
Because "inference" only resolves inside this Compose network. Hardcoded, the image breaks
anywhere else; from the environment the same image works in Compose, standalone, or in dev
against 127.0.0.1:8000.

5. Only mlflow and frontend publish a port to the host. inference doesn't. Why not, and how does
the frontend still reach it?
Nothing outside Docker calls inference, so publishing would only widen exposure. The frontend
reaches it over the Compose network at inference:8000.

6. depends_on here only waits for the mlflow container process to start, not for the tracking
server inside it to be ready to accept connections. If your serve.py tries to load the Staging
model at startup and mlflow isn't ready yet, what happens to the inference container? Look at
docker compose logs inference if it fails.
It exits. Observed status "Exited (1)", logs showing RESOURCE_DOES_NOT_EXIST: Registered Model
with name=food11 not found. Nothing retries, so the container just dies. A healthcheck plus
depends_on: condition: service_healthy, or a retry loop at startup, fixes it.

7. Run docker compose ps. Which services have a published port listed, and which don't? Does
that match what you'd expect from the docker-compose.yml?
mlflow 0.0.0.0:5000->5000/tcp and frontend 0.0.0.0:8501->8501/tcp are published; inference shows
only 8000/tcp. Yes, it matches: ports: is declared for those two and not for inference.

8. Refresh the frontend and upload an image again. Does the prediction come from the new model
version, or the old one? Your serve.py loads the model once, at startup - what single command
lets you pick up the new Staging version without rebuilding any image?
The old one. Same bread image gave Bread 55.94786405563354% before and after promoting the new
version, identical to the digit, so it was still the model held in memory.
Command: docker compose restart inference.

9. Why does restart alone work here - no rebuild needed? What does that tell you about what's
baked into the inference image versus fetched at container startup?
The image holds only code and dependencies; the weights are resolved from the alias and
downloaded from mlflow at process start. Restarting replays that. After the restart the same
image answered Vegetable-Fruit 89.7% from the new version. A rebuild is needed only when
serve.py or the dependencies change.

10. Is your registered model and its Staging assignment still there after this down/up cycle?
Now try docker compose down -v followed by docker compose up - what's different this time, and
why?
After down/up: still there, versions 1, 2, 3 with champion on 3, because down keeps the volume.
After down -v: gone. The volume lab1_mlflow-data was removed, so the stack came back with no
registered models, only the Default experiment, and inference exited again. -v deletes the
declared volumes, which is where the sqlite db and the artifacts live.

11. This compose file is still meant to run on one machine. What would have to change for the
inference service to run as three replicas behind a load balancer, or for the mlflow service to
survive a machine failure?
Compose has no multi-host scheduling, no load balancer, no rolling updates and no rescheduling,
so if the host dies mlflow dies with it. You would need an orchestrator (Kubernetes, Swarm,
ECS), a service/ingress in front of the inference replicas, and mlflow backed by a real database
and object store instead of sqlite on a local volume, which replicas cannot share anyway.
